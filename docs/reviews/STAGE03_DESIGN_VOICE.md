# Stage 03 independent design voice

Independent Codex-family design review of the Stage 03 contract before its “Review outputs” heading. No prior review artifacts were read. This is a source-based review of proposed functionality; no implemented PM interface or browser validation is claimed. Stage 04 and a shell redesign are excluded.

Inspected: `apps/web/src/app/projects/[id]/page.tsx`, `components/project-editor.tsx`, `components/project-form.tsx`, `components/shell.tsx`, `components/session.tsx` (AuthGate), `components/ui/button.tsx`, `app/globals.css`, `lib/api.ts`, `app/api/v1/[...path]/route.ts`, `tests/projects.spec.ts`, `tests/teams.spec.ts`, `tests/helpers.ts`, and `playwright.config.ts`, all under `apps/web`.

| Dimension | Assessment of the proposal against existing source |
|---|---|
| Information architecture | Keeping Product Plan inside project detail preserves context. The current page has one overview and a future panel; a schema covering requirements, epics, stories, criteria and uncertainty needs an explicit reading order and section navigation. |
| All interaction states | Empty, configuration, real running, failure, unknown outcome, saved draft, approved, superseded, conflict and Viewer states are named. Dirty editing, selecting another version during editing, and approval while local text differs from the saved revision remain underspecified. |
| User journey | Explicit Generate → review → edit → Save → exact Approve → reload is coherent. A later reader opening the approved version and an author opening their newly generated draft are distinct entry points and need visibly different version context. |
| AI slop / specificity | No invented thinking steps, usage or certainty is a strong boundary. Field-level provenance and actual input snapshots are useful only if readers can inspect what each label refers to without drowning the document in badges. |
| Existing design-system alignment | Existing Button variants, semantic light/dark tokens, panel borders, native labels and details fit this work. New nested editors need textarea, fieldset and validation styling; `.standard-form` currently styles inputs/selects but does not give textareas equivalent surface treatment. |
| Responsive intention | One column is appropriate. Current CSS already adapts at 720px and gives mobile buttons 44px targets, but long source quotes, local keys, metadata and several version actions need explicit wrapping rules. Current screenshots cover the home screen. |
| Accessibility | Shell already supplies a skip link, mobile focus containment, Escape and focus restoration; AuthGate keys protected state by account/workspace/path. Nested field names, hidden invalid sections, completion announcements and approval confirmation focus need their own behavior. Existing tests do not establish those PM interactions. |

**Ranked concerns**

1. **P1 — Define the saved artifact before enabling approval.** The contract forbids autosaving approval but does not specify the screen when a saved revision has unsaved edits. Extend the planned ProductPlan state model with viewed version/revision, dirty state and save outcome. Disable approval while dirty, with “Save changes before approving”; after Save, show the returned revision. Confirmation should identify “Approve version 3, revision 7” and unresolved/explicitly deferred confirmation items. Version selection, opening a generated draft and creating a historical copy must offer Save, Discard or Keep editing within the same authorized project. Account/workspace changes and sign-out must still clear protected text through AuthGate.

2. **P1 — A full-document editor needs recoverable structural errors.** The proposal allows removing requirements/stories and editing dependency keys while validating references and cycles. A generic failed-save message would strand a large draft. Specify server field paths tied to stable node keys, an error summary linking to labeled fields, and automatic expansion of invalid details. Before removing a referenced item, list the affected stories and require the user to repair references; never silently cascade their text away. Keep every other local field intact. `ProjectEditor` is a useful small-form baseline, not a sufficient error model for this document.

3. **P1 — Make run recovery actionable without another charge.** `lib/api.ts` currently exposes an error message/status and discards structured run/category data; its POST failure copy directs users to Projects. The proxy also returns a generic uncertain-operation message. The planned timeout change alone cannot implement Check Status. Add a PM-specific typed result/error contract retaining safe run references and the client request UUID. Render failed, still running, interrupted and outcome unknown separately, with GET-based Check Status and an explicit new-request action only where appropriate. Keep the readable approved plan visible when a new run fails. Test reload reconciliation and delayed completion, not just the successful live flow.

4. **P2 — Make source freshness and provenance inspectable.** The current overview calls the editable description “Your original project description.” Stage 03 introduces an immutable generation snapshot, so that wording becomes misleading after edits. Use “Project description” for the current field and “Inputs used for version 3” for the snapshot. A visible freshness notice should state that current project details differ. Provenance labels should say “From supplied brief,” “Suggested,” “Assumption” or “Edited by …”; an expandable excerpt identifies the actual input. Avoid “Verified” or implying a quote proves the requirement follows from it.

5. **P2 — Specify document hierarchy before building repeated cards.** Use one Product Plan header showing state, version and revision; then Overview, Requirements, Epics and stories, and Review items. Keep generation inputs, run history and execution metadata in separate native disclosures. Keep unresolved blocking confirmations visible beside the approval action rather than buried in a collapsed section. Use a compact anchor list for long plans. On mobile, stack actions, wrap keys/quotes, and keep all form controls inside the viewport. Extend the current Chromium/mobile/tablet browser coverage to a substantial multi-epic plan and both themes.

6. **P2 — Define focus and announcement rules for asynchronous changes.** Give each repeated control a unique accessible name through fieldset legends and story identifiers. Announce actual run completion and Save success through a concise status region; errors use an alert and linked summary. Do not steal focus when a background status check completes. An explicit Open draft action may focus its heading. Approval confirmation must be keyboard operable, identify its target, and restore focus on cancel. Exercise these with keyboard-only browser tests, including expanding an invalid collapsed story and stale-revision recovery.

**Taste choices**

- Prefer a native labeled version select with state and date in each option over tabs that grow with history. Keep the current approved version as the default reader view; explicitly open a newly generated draft for its initiating author.
- Endorse C05: “Create editable copy” makes immutable historical content correctable without requiring another model request. Show its source version and human-copy origin.
- Use restrained text labels and inspectable excerpts for provenance. Preserve the existing green accent for actions/status; do not make color the only distinction between draft, approved and suggested content.
