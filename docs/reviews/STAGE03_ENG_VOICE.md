Ranked gaps follow. None is presented as an executed Stage 03 failure.

1. **HIGH — Final authorization must serialize with logout.** **Evidence:** C:79 promises logout during execution prevents publication; `security.py:52-65` performs an unlocked session/user read, while `auth.py:148-151` revokes the session without a workspace lock. Workspace serialization alone therefore cannot protect a future read-check-commit sequence from concurrent logout. **Recommendation:** define publication's linearization point; under the workspace lock, lock/re-read the initiating session and active user in a documented order, then check expiry and role before the atomic publication commit. Test logout committed before finalization and logout blocked behind finalization, plus expiry/demotion/removal schedules. **Confidence:** high, design gap inferred from inspected locking. **Tradeoff:** logout can briefly wait for bounded finalization; already-consumed provider tokens remain possible.

2. **HIGH — Release authentication state and close every reservation crash window.** **Evidence:** `db.py:21-23` yields a request-lifetime Session; `security.py:68-75` returns its ORM identity. C:65 persists pending before running/deadline, while C:77-81 requires expiry and immutable terminals. **Recommendation:** snapshot scalar IDs, explicitly end the dependency transaction before SDK await, and never reuse its ORM identity afterward. Assign a finite deadline in the first durable pending reservation. Use fresh short sessions for every phase, conditional active/unexpired transitions, and atomic draft-plus-success persistence. After uncertain commit, reconcile by run ID in another session; never overwrite committed success. Test crashes between both commits, expired/reconciled leases and late replies across app instances. **Confidence:** high, future lifecycle gap. **Tradeoff:** more explicit transaction code, without a worker framework.

3. **HIGH — Separate replay identity from changing execution snapshots.** **Evidence:** C:62-63 snapshots the project before comparing the client key; C:50 requires an immutable request hash, and C:91 snapshots context revisions. **Recommendation:** persist a canonical hash of validated explicit client inputs separately from the immutable execution snapshot/hash. Replay compares against the original request without rebuilding its hash from current project text, context content, model configuration or prompt version. Define normalization and absent-versus-empty semantics. A new key captures fresh state; changed explicit inputs under an old key return 409. Test identical replay after project/context edits and configuration changes, including admission saturation. **Confidence:** high, design ambiguity. **Tradeoff:** two clearly named hashes prevent misleading payload conflicts.

4. **HIGH — Give every editable node stable provenance identity.** **Evidence:** C:46 requires server comparisons of stable keyed nodes, but C:54 lists no criterion key; only stories explicitly require stable keys in C:44. **Recommendation:** define persistent identities for requirements, criteria and confirmation items as well as epics/stories; scope incoming identities to the plan and reject foreign IDs. Compare content independently of order, ignore client origin claims, preserve unchanged/moved origins, and assign actual human actor to changed/new content. Store human blocker resolutions/deferrals with actor and reason. Preserve copied input evidence and source revision/hash independently of later source-draft edits. Test insertion, reorder, deletion, key substitution and mixed-origin copying. **Confidence:** high, schema specification gap. **Tradeoff:** modest identity metadata avoids positional provenance corruption.

5. **HIGH — Specify enforceable relational and graph invariants.** **Evidence:** C:50 names a run/project/workspace composite FK, but C:51 only describes a generating-run FK and a same-project copy source; C:53 stores story keys beneath epics although dependencies cross epics. **Recommendation:** name same-project composite constraints for generating runs and copy sources; enforce plan-wide story-key uniqueness, potentially with a plan ownership column and composite epic FK. Define check constraints for states, approval metadata and allowed creation origins. Validate requirement references, self-dependencies/cycles and every criterion on assembled documents before save/approval; revalidate reads without silently repairing corruption. **Confidence:** high, future integrity gap. **Tradeoff:** slightly richer constraints prevent application-only cross-project assumptions.

6. **HIGH — Persist copy identity and serialize revision decisions.** **Evidence:** C:162 requires persistent copy-request recovery, but C:51/110 defines no stored copy-request identity. C:112 requires atomic approval and monotonic versions. **Recommendation:** add a durable scoped copy UUID, original source revision/hash and unique constraint. Duplicate keys return the original copy even if subsequently approved; an intentional new copy needs a new key. Allocate versions for generation/copy under the same workspace lock. Fetch fresh plan state after locking and condition saves/approval on exact revision/state; supersede the previous approval atomically. Clarify that approval versions cannot regress behind the current approved version. Test save-versus-approve, dual approval and copy-versus-generation. **Confidence:** high, design gap. **Tradeoff:** duplicate recovery may return an immutable original copy rather than an editable one.
