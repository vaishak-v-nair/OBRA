# Password policy independent engineering review

Reviewed the current plan and application/schema/auth/form/test/gate source only. No prior review artifacts were read. No tests, database operations, model calls, source edits, or Git mutations were performed. This is a planning review, not implementation verification.

Verdict: APPROVE implementation direction, with the acceptance refinements below. The change needs no migration, credential rewrite, new service, password-change endpoint, or authentication refactor.

| Judgment | Assessment and code-backed acceptance |
|---|---|
| 1. Architecture | PASS. `apps/api/orba/schemas.py:43-55` already separates login schema from registration policy, so an annotated reusable `NewPassword` with published 15/128 bounds and a whitespace-only validator is sufficient. Override only the registration password field; retain login's 1/128 field. `User.password_hash` is already Text (`models.py:52`), so no schema change is justified. Verify generated OpenAPI includes distinct registration/login limits; a private validator alone would leave creation's published minimum incorrect. |
| 2. Tests | PASS WITH REFINEMENTS. Existing hash/cookie and policy tests (`test_auth_workspaces.py:39-88`) do not cover new boundaries or legacy compatibility. Add real-PostgreSQL cases for 14/15/64/128/129, astral Unicode, leading/trailing spaces, whitespace-only rejection, and exact-value login. For accepted values, verify the complete value against the stored salted Argon2id hash and reject truncated, stripped, or canonically altered alternatives. For rejected registration, assert both user and session counts remain unchanged. Existing browser helpers use only a normal ASCII password (`tests/helpers.ts:6`); add explicit keyboard, paste, over-limit correction, long login, legacy login, and server rejection cases in every configured viewport. |
| 3. Performance | PASS. Length enforcement stays before `rate_limit` and Argon2 work through request validation (`auth.py:114-118`). Keep the same Argon2 parameters and persisted throttle behavior; raising the creation minimum introduces no new query or hashing loop. Native maxlength removal needs a code-point scan only on submission, before the busy lock and before any CSRF fetch/POST. Do not add live counters, debouncing, dependencies, benchmarking infrastructure, or model probes for this bounded change. |
| 4. Security and compatibility | PASS WITH REQUIRED PRECISION. Registration passes the exact password into Argon2 (`auth.py:118`); login verifies before an eligible parameter rehash (`auth.py:134-139`). Test current-parameter legacy hashes remain byte-identical after login; separately seed a genuinely older eligible Argon2 parameter hash and prove normal login upgrades it without imposing creation length. Existing sessions must authenticate before login. Login's ordinary rotation revokes the supplied old session (`auth.py:27-44`), so do not assert that session remains active afterward; assert expected rotation and preservation of an unrelated pre-existing session instead. Never use fixture hashes as live model evidence. |
| 5. Errors and UI behavior | PASS WITH REFINEMENTS. `auth-form.tsx:18` currently locks before validation; move policy validation ahead of the lock and preserve entered values on all errors. Both modes need code-point upper-bound validation after removing `maxLength` (`:28`). Signup alone applies the 15 minimum and whitespace guard. Python `isspace()` and JavaScript `trim()`/whitespace regexes do not have identical character sets: avoid introducing stricter client rejection of server-valid values; use length-only client validation with the authoritative server whitespace guard, or deliberately align and test the character sets. Associate help and field errors with the input, expose invalid state, and focus it for password validation errors. Server detail fields are `body.password` (`main.py` validation handler); map those deliberately rather than marking every failed login/network request as a password policy error. Prove invalid submission sends zero POSTs, corrected submission works, and no automatic retry occurs. |
| 6. Rollout and evidence | PASS. Existing `conftest.py` and `scripts/test_database.py:6-21` supply a guarded migrated real PostgreSQL boundary; reuse them. A browser legacy seeder must invoke that guard before constructing an engine/connecting and must add narrowly scoped identified fixtures without resetting development data. Append mandatory identities to active `stage031_backend` and `core_browser`; `verification.py:255-269` selects those lists. Preserve historical lists and cases. Run backend and browsers sequentially through complete Gate A, retain failures and actual counts, and publish new source-bound evidence. Changed source cannot inherit old live certification; Gate C remains PARTIAL with the historical failed live attempt retained. No paid call is needed or authorized. |

The most material implementation risks are an accidental login minimum increase, incorrect legacy session-preservation assertions that disable normal rotation/rehash, Unicode disagreement between browser and API, and new tests omitted from the active mandatory baseline. The plan addresses each with the refinements above. Keep production changes confined to the reusable creation type and existing auth form; use additive test code and existing verification infrastructure.
