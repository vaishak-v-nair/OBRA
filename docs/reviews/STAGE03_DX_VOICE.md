# Stage 03 developer-experience source review

Planning review only. No application commands, migrations, provider calls or tests were executed for this review. The plan records a Stage 02 regression baseline; its 25.79-second backend and 1.8-minute browser durations are **not onboarding measurements or Stage 03 evidence**. Provider configuration was reported absent at intake by the plan; I did not inspect secret files or independently recheck it.

Review limitation: the first plan read stopped before `## Review outputs`, but a later search accidentally exposed CEO/Design summary lines 178–207. No other DX review was read. This review is source-grounded and must not be described as blind to those prior-phase summaries.

Ranked findings:

1. **High — Fix the verification interface before implementation.** `scripts/verify.ps1` has no modes and stops at the first nonzero command; `apps/api/pyproject.toml` discovers `tests`, while `apps/web/playwright.config.ts` discovers the shared browser directory. The plan requires separate core/live checks but supplies no exact invocation or discovery exclusion. Define one documented interface, for example `pwsh -File scripts/verify.ps1 -Mode Core` and `-Mode Full`, with Full the default. Core must explicitly report “core only; live unverified”; Full must retain nonzero BLOCKED when credentials/live evidence are unavailable. Keep live API/browser suites out of ordinary discovery by explicit configuration, not skipped tests. Run core and each live suite sequentially against guarded `orba_test`; report each exit/count/not-run reason. Preserve a separate literal exit-1 experiment. Provider doubles establish lifecycle/error behavior, never live generation.

2. **High — Publish the actual first-success journey and measure it.** `README.md` already covers frozen install, PostgreSQL startup, environment-file creation, migration, two terminals, exact localhost origin, registration and workspace creation. Append project creation → Product Plan → explicit Generate → edit/save → approval/reload, including the role required at each step. Explain locally setting `ORBA_PM_API_KEY` and a model actually available to the account, then restarting the API; never print the key. `orba/config.py` currently has no PM settings and ignores extra environment fields, so require explicit aliases/tests for the documented names and safe missing/invalid-model guidance. A configured capability is not a connectivity check. Proposed targets, **unmeasured**: prerequisite-ready checkout to persisted project ≤15 minutes; running stack with valid provider access to first persisted generated draft ≤5 minutes. Record start/finish definitions, tool versions, cold-cache/install time and provider latency separately. Account provisioning has unknown duration; do not hide it in a claimed TTHW.

3. **High — Make the recovery envelope survive transport.** `apps/web/src/lib/api.ts` flattens validation details and `ApiError` retains only message/status; its POST network message always directs users to Projects. The proxy already forwards `Retry-After`, but the client discards it. Add typed optional code, field paths, run/diagnostic IDs and retry delay, preserving the current simple project callers. Provide category→action mappings: missing configuration→local setup/restart; invalid field→focus field; admission limit→wait; unknown outcome→GET reconciliation; stale revision→retain local text and compare/reload; lost membership→clear protected content. Never translate an unknown outcome into another paid POST. Document that replaying an old request UUID retrieves its run; a deliberate new attempt after a terminal failure uses a new UUID. Cover client/proxy behavior with application-path tests. Evidence: client/proxy files and the plan's frontend/API contracts.

4. **High — Give timeout settings one executable invariant.** Current proxy/client budgets are 15/20 seconds (`apps/web/src/app/api/v1/[...path]/route.ts`, `src/lib/api.ts`); proposed provider timeouts reach 180 seconds. “Longer than” is insufficient for copy-paste configuration. Specify validated provider, pending/running lease, DB finalization and transport budgets with their exact environment names and maximums. Account for connection/admission/finalization time, and test the boundary through the real proxy. Restrict the longer budget to generation POST. On a transport timeout, retain the UUID and check status; do not claim provider cancellation or unchanged billing. Keep normal request timeouts intact.

5. **Medium — Expose migration side effects and readiness scope.** `scripts/verify.ps1` executes `alembic upgrade head` and drift checking before isolated tests, using configured development settings. Label that mutation prominently in README and the command help; preferably separate explicit local migration from a core test command. Confirm the intended database identity without printing connection secrets. Preserve the additive, populated Stage 02 upgrade/repeated-upgrade test and named constraints promised in the plan. Extend guarded cleanup in `scripts/prepare_tests.py` for new FK tables. Extend `orba/main.py` readiness beyond its current Stage 02 columns to the required PM schema, while keeping provider capability/configuration separate from DB readiness. No reset or downgrade is a recovery shortcut.

6. **Medium — Consolidate the operating guide where developers start.** Update README's Stage 02 title, future-AI copy and obsolete authorization statement when Stage 03 is authorized/implemented. Link a short PM setup/troubleshooting/test guide from README, API docs and the configuration empty state. Include exact core/full commands, placeholder-only request examples with cookie/Origin/CSRF prerequisites, field bounds, safe diagnostic lookup procedure and upgrade limitations. Keep uncertain-write recovery next to each write example. Lockfiles plus `--locked`/`--frozen-lockfile` remain authoritative; state tested tool versions separately from broad supported ranges. Evidence: README, `verify.ps1`, API/web package manifests and test entry points.

Genuine taste choices: `pm-runs`/`pm-plans` versus longer resource names; `/draft` versus `/draft-copies`; a two-mode script versus separate core/live wrappers. Current project-scoped naming is reasonable. Choose once and use identical names in OpenAPI, client helpers, logs and documentation. These preferences do not relax authentication, no-auto-retry, migration preservation or mandatory live evidence.
